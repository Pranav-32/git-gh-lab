Level 1 · Forking on GitHub

What Is Forking?

Forking makes a server-side copy of someone else’s repository: GitHub copies it into your own account, as your remote repo. Nothing is downloaded to your laptop, and the original stays untouched.

Why fork?

No permission needed

Work on any public project, even one you can’t push to.

Experiment safely

Try ideas and break things in your copy, not theirs.

Contribute back

Offer your improvements to the original with a Pull Request.

14

What is cloning? Cloning downloads a repository from GitHub to your laptop: every file plus the full commit history. Then you can edit, run and commit on your own machine, even offline. The animation: Srevarshan runs git clone https://github.com/Srevarshan05/Clutch.git (his fork from the previous slides). The files (src/, docs/, clutch.toml...) and the history travel down to his laptop as a Clutch/ folder. Git also remembers where it came from: the GitHub address is saved as a remote called origin, so later git push and git pull know where to go. Fork vs Clone, in one line each: - Fork = a copy on GitHub's servers, in your account. Done with the Fork button (or gh repo fork). Used to get your own copy of someone else's project. - Clone = a copy on your laptop. Done with git clone. Used to actually work on the code. They are not either/or. The usual flow is: fork on GitHub, clone your fork, edit, commit, push. If the repo is already yours (like the one from the website/CLI demo), you skip forking and just clone. Note for slow or unstable networks: a partial clone (for example git clone --filter=blob:none <url>) skips old file contents at first. git backfill (Git 2.49+) then pre-downloads the missing historical file contents in efficient, compressed batches.

Level 2 · Branching

Branching Explained with Marvel’s Loki TVA Analogy

Like the Time Variance Authority (TVA), Git protects one Sacred Timeline, while branches grow as variant timelines.

The 3 Core Commands

git switch -c new-ai

git switch -c → Create and switch to a new branch.

git commit -m "feat: add AI feature"

git commit → Record a milestone in your current branch.

git push -u origin new-ai

git push → Publish your branch to GitHub.

The timeline collision 💥

Merge Conflict

Developer A changes the header to BLUE.

Developer B changes the same header to RED.

Git cannot determine which change is correct. A developer must resolve the conflict.

The timeline animation loops through the sequence: 1. Sacred Timeline appears. 2. It splits into two universes. 3. AI and theme developers work independently. 4. Both modify the same line of code. 5. A red collision. 6. The conflict is resolved and the changes are merged. “A branch is like a parallel universe where we can work independently. If two universes change the same part differently, Git may need human help to merge them.” The 3 core commands: git switch -c new-ai · git commit -m "feat: add AI feature" · git push -u origin new-ai. Note: Different branches do not guarantee conflict-free merging. Conflicts depend on the changes being merged.

Level 2 · Reviewing a Pull Request

Inside a Pull Request: Review, Then Merge

A PR is a page on GitHub where the owner sees your changes, comments on them, and decides whether they join main.

What you see in a PR

Conversation for discussion, Commits for the history, and Files changed for every added (green) or removed (red) line.

Looks good

Approve → Merge pull request → the changes join main.

Needs work

Request changes → the review goes back to the requester → they push a fix to the same branch → the PR updates → review again.

PRs power open source

git stash puts your unfinished, not-yet-committed changes aside and cleans your folder. Later, git stash pop brings them right back.

When do you need it?

You’re halfway through the dark-mode feature. Suddenly: “Urgent! Fix the login bug on main.” Your work isn’t ready to commit, and switching branches now would drag the half-done changes along.

🗄️

Bring it back, keep a copy on the shelf

22

What is git stash? It puts your unfinished, not-yet-committed changes on a shelf and leaves your working folder clean. Later, git stash pop brings them back. The story: you're halfway through the dark-mode feature (style.css and theme.js are half done). An urgent message arrives: fix the login bug on main. The work isn't ready to commit, and switching branches now would drag the half-done changes along (or Git may refuse to switch). The animation, step by step: 1. git stash: the two half-done files move to the stash shelf as stash@{0}. The folder becomes clean. 2. git switch main. 3. Fix the bug and commit it: git commit -am "Fix login bug". 4. git switch dark-mode. 5. git stash pop: the two files come back, exactly as you left them, and the shelf is empty again. Analogy: putting half-finished homework in a drawer, dealing with the urgent task, then taking it back out. Commands: git stash (save), git stash list (see the shelf: stash@{0}, stash@{1}...), git stash pop (bring back and remove from the shelf), git stash apply (bring back, keep a copy on the shelf). Good to know: by default stash only saves files Git already tracks. Brand-new files need git stash -u (include untracked).

Level 3 · Force Push

Replacing GitHub’s History: Force vs Force-with-lease

After git commit --amend, your laptop’s history no longer matches GitHub’s, so a normal git push is refused. To replace GitHub’s version, you force it, and there’s a careless way and a careful way.

--force = “Replace it, no questions asked.”

It never looks at GitHub first. If a teammate pushed in the meantime, their work disappears.

--force-with-lease = “Replace it, only if nobody changed it.”

It checks GitHub still looks the way you last saw it. If not, it stops and nothing is lost.

Rule of thumb: always prefer --force-with-lease, and only rewrite branches that you alone are working on.

26

Why do we need force at all? After git commit --amend (previous slide), the laptop has a new commit B′ instead of B. GitHub still has B, so the two histories disagree and a normal git push is refused. To make GitHub accept B′, we force it. The animation (both sides play the same story): 1. GitHub and the laptop both have A → B. 2. You amend B, so on your laptop it becomes B′. 3. Meanwhile, Pranav pushes his commit C to GitHub. 4. You force-push B′. 5. Left, git push --force: it doesn't check anything. GitHub becomes A → B′, and Pranav's C is deleted for everyone. Right, git push --force-with-lease: it first checks "is GitHub still A → B, the way I last saw it?" No, C is new, so the push is stopped and nothing is lost. Get Pranav's work first (git pull), then push again. Say it simply: --force = "replace it, no questions asked". --force-with-lease = "replace it, only if nobody changed it since I last looked". Rule of thumb: prefer --force-with-lease, and only rewrite branches you alone are working on. It's a safety check, not a licence to rewrite shared history.

Level 3 · Git Rebase

Git Rebase, Explained with a Simple Sandwich Analogy

Taking the sandwich apart to remove the tomato, then stacking it back up perfectly, is an interactive rebase (git rebase -i).

27

Start with the story on the left, then let the animation on the right play it out. Each story step lights up while the sandwich does the same thing. The animation runs slowly (about 6 seconds per step); use the Pause / Play button at the top-right of the story panel to stop on any step. The Sandwich Surgery vs. Git Rebase. When you take the sandwich apart to remove the tomato and stack it back up perfectly, you are doing an interactive rebase (git rebase -i). 1. You build the original sandwich layers: Bread, Tomato, Cheese, Mayo, Pickles. In Git: you made 5 separate commits in your history, one for each ingredient layer you added. 2. Person B says: "I don't like tomatoes, please fix it." In Git: the client or code reviewer looks at your project and says: "This specific commit in the middle breaks the rules, delete it." 3. You carefully lift off the Pickles, the Mayo and the Cheese, and set them aside on a clean plate. In Git: Git un-stacks your recent commits and holds them temporarily in the air. 4. You grab the Tomato layer, throw it in the trash, and wipe the bread clean. In Git: you select the tomato commit and tell Git to drop it from the history. 5. You take the Cheese from the side plate and put it back onto the base Bread. In Git: Git applies your cheese commit directly onto the bread. 6. You place the Mayo back on top of the cheese, and finally the Pickles back on top of the mayo. In Git: Git applies the remaining commits back down, one by one, in the exact same order. The result: your final sandwich is now perfectly stacked: Bread, Cheese, Mayo, Pickles. To Person B, it looks like magic. They never see the tomato, and they don't see the mess of you taking it apart. It looks like you built it perfectly without tomatoes from the very first second. That is exactly what a Git rebase does: it rewrites history to make it look clean. Careful: the rebuilt commits get new IDs (hashes). Only rebase a branch you alone are working on; if you already pushed it, push with git push --force-with-lease (previous slide). If students ask for the exact command: git rebase -i HEAD~4 lists the last 4 commits (Tomato, Cheese, Mayo, Pickles). Change "pick" to "drop" on the Tomato line, save and close.

Choosing Your Actions: pick, drop, reword, squash

Run git rebase -i HEAD~5 and Git opens a checklist: your kitchen menu. It reads top to bottom, oldest commit first. To choose a mode, replace the word pick with a new command word.

pick

To combine

→

Change pick to squash. Git blends the Pickles into the Mayo above it.

Tip 1

The order matters: the oldest commit is at the top. Git applies the Bread first, handles the Tomato, and builds its way up.

Tip 2

Shortcuts allowed: you don’t have to type the whole word. Just type one letter: p, d, r or s.

28

Step 2: choosing your actions in the editor. Once you run git rebase -i HEAD~5, Git pauses and opens a configuration text file. This file is your kitchen menu checklist. Git reads it from top to bottom (oldest commit to newest). To choose a mode, delete the word pick and type your new command word instead. The edit screen, before vs after (the animation changes one word at a time): pick 1a2b3c Bread → pick (keep) pick 4d5e6f Tomato → drop pick 7a8b9c Cheese → pick (keep) pick 0d1e2f Mayo → reword pick 3a4b5c Pickles → squash The rules: - To keep (pick): do absolutely nothing. Leave the line alone. - To delete (drop): change pick to drop (or just delete the whole line). Git throws the Tomato away. - To rename (reword): change pick to reword. Git pauses later and lets you change Mayo to "Lite Mayo". - To combine (squash): change pick to squash. Git blends the Pickles into the Mayo above it. Pro tips: 1. The order matters: the oldest commit is at the top. Git applies the Bread first, handles the Tomato, and builds its way up. 2. Shortcuts allowed: type a single letter instead of the word: p, d, r or s. Save and close the editor to start the rebase. If Bread is the very first commit in the repository, use git rebase -i --root instead of HEAD~5.

Fix a Typo in Your Last Commit

Make a small mistake on purpose, then fix it with git commit --amend.

LEVEL 3

10:00

1

Check your status

Add a typo on purpose

Open README.md, add this line, and save.

3

Commit the mistake

Save it as a normal commit, typo and all.

git add README.md
git commit -m "feat: add project runtime details"

4

Fix it and amend

Change Gitt to Git, save, then amend.

git add README.md
git commit --amend -m "feat: add correct project runtime details"

Check your history

Push to GitHub

Then check the fix on GitHub.

git push origin main

Done when: the typo is fixed, git log shows one corrected commit, and the fix is on GitHub.

Level 3 Hands-on Practice — 10 minutes. Leave this slide up while students work. The six steps, in order: 1. git status: the folder should be clean. 2. Open README.md, add the line "This project runs on Gitt." (with the typo) and save. 3. Commit the mistake: git add README.md, then git commit -m "feat: add project runtime details". 4. Fix Gitt to Git, save, then git add README.md and git commit --amend -m "feat: add correct project runtime details". This replaces the last commit instead of adding a new one. 5. git log --oneline: only the corrected commit shows, and its ID (hash) is different from before. 6. git push origin main, then check the fix on GitHub. Instructor notes: • Students push to main: in the Level 2 practice they merged their branch and deleted it, so main is the only branch left. • The task is designed so students amend a local commit before pushing it, so a normal push works. Do not require force push here. • If a student already pushed the typo commit before amending, the normal push will be refused. That's the situation from the force-push slide; guide them through git push --force-with-lease origin main on their own practice repo.
